## Problem Statement

Krish needs a final ML lab project: a 5-minute live demonstration of implemented machine-learning algorithms and their pipelines, run from a Google Colab notebook (no PowerPoint), followed by questions from classmates and a viva. Marks depend on it. Krish describes themselves as new to ML ("i didnt paid attention to my ML classes"), so every line of code must be explainable, and a viva guide is part of the deliverable.

The project is a webcam rock-paper-scissors game in which the bot predicts the human's next move and plays the counter. Real data shows people are predictable: in a 2014 study of 72 people playing 300 rounds each, players repeated their previous move 52.7% of the time right after losing, against 33.3% if they were random.

## What Makes This Cool

- The opening line of the demo, in Krish's words: "after loosing, people repeat the same move 53 percent of the time", and the bot uses that habit against you.
- A classmate plays live on camera against the bot, and the bot's win rate climbs above the 33% luck line as it learns them.
- Two real ML pipelines, each a complete lab-style workflow: the **eyes** (recognise the hand gesture from the webcam) and the **brain** (predict the next move). Every lab algorithm has a job and a story. Find-S works out the definition of "scissors" from finger positions, the Perceptron fails at the brain task for a reason worth explaining, and Linear Regression measures how fast the bot learns a person.

## Premises

1. Classical scikit-learn algorithms from the labs, not deep learning. MediaPipe's pretrained hand-landmark model is used only as a feature extractor: it turns a photo into 21 points on the hand. We do not train it, and the notebook says so.
2. Two public datasets carry the lab-style training results. The live game uses the trained models.
3. Honest baselines everywhere. The brain's ~45% accuracy is always shown next to 33.3% for luck and 35.6% for "always rock".
4. The notebook is the presentation. It is saved with outputs, so it can still be shown if a cell misbehaves live.

## Recommended Approach

### Datasets

1. **Eyes: TensorFlow "rock_paper_scissors" images** (Laurence Moroney, CC BY 2.0).
   - 2,520 training and 372 test CGI hand images, 300×300 px, labelled rock, paper or scissors.
   - Download: `https://storage.googleapis.com/download.tensorflow.org/data/rps.zip` (200 MB) and `rps-test-set.zip` (29.5 MB). Both links checked today.
   - A one-time script reads each image with OpenCV (`cv2.imread`, then BGR to RGB) and runs the MediaPipe HandLandmarker on it. It writes `data/hand_landmarks.csv`: one row per image, with 21 × (x, y, z), the label and the original split.
   - Images where no hand is found are dropped, and the count is reported in the notebook.
   - The notebook shows this code behind `REBUILD_HAND_DATA = False` and loads the CSV by default.
2. **Brain: Wang, Xu & Zhou (2014)**, "Social cycling and conditional responses in the Rock-Paper-Scissors game", *Scientific Reports* 4:5830 (arXiv:1404.5199).
   - Distributed as `data.WXZ2014` in the CRAN package stratEst 1.1.8 (GPL-3).
   - 21,600 rows: 72 players × 300 rounds, with random pairwise matching each round.
   - Columns: `id`, `game`, `period`, `choice` (r/p/s), `other.choice`, `result` (win/lose/tie), `input`.
   - Already converted to CSV by a working stdlib R-file reader, which becomes `tools/rda_to_csv.py`. Output: `data/rps_human_games.csv`.
   - Checked today: rock is chosen 35.7% of the time. Players repeat their last move 52.7% of the time after a loss, 43.3% after a tie and 36.0% after a win. The `result` column agrees with the game rules on 100% of rows.

Both CSVs are committed with attribution and licence notes in the README.

### Notebook structure (`MindReader.ipynb`)

**0. Opening.** Title, the 53% hook, one install cell (`pip install mediapipe`, plus downloading the `hand_landmarker.task` model file), then imports.

**Part 1: The Eyes.** The lab steps, run on `hand_landmarks.csv`.
- Load the data, then `head`, `tail`, `shape`, `info`, `describe`, null checks, duplicate checks and class counts.
- Features:
  - Landmarks made relative to the wrist and normalised for hand size.
  - Five finger up/down booleans: a finger counts as up when its tip is farther from the wrist than its middle joint.
  - Five finger-extension distances.
- Exploration: a countplot of the classes; histograms and boxplots of finger extension; a boxplot of each finger by gesture; a correlation heatmap; a pairplot of 3–4 features coloured by gesture.
- Find-S (Lab 3) on the finger booleans, with "scissors" as the target concept. It prints the hypothesis after each example, the same way the lab did.
- An 80/20 stratified split. Using TensorFlow's official train/test split instead is the builder's call.
- Models, each in a Pipeline with StandardScaler: Gaussian NB, Decision Tree, Perceptron, Logistic Regression, and SVM (linear and RBF).
- For each model: train vs test accuracy, precision, recall and F1, collected in a comparison DataFrame and bar chart.
- For the best model: confusion matrix, classification report and ROC curves (via `label_binarize`). `plot_tree` for the Decision Tree.
- GridSearchCV (SVM `C`, `gamma` and kernel; tree depth and criterion), 5-fold `cross_val_score`, and a learning curve.
- Predict one new sample with `predict_proba`.

**Part 2: The Brain.** The lab steps, run on `rps_human_games.csv`.
- Load the data, then `head`, `tail`, `shape`, `info` and `describe`. Null checks: the first round has no previous move. Class counts show the rock bias.
- Exploration:
  - choice and result distributions
  - repeat rate by last result (the 53% bar chart)
  - heatmaps of last move → next move, split by last result
- Features: the player's last two moves, the opponent's last move and the last two results. There is also a "relative" version that codes the next move as stay, shift up or shift down; the notebook explains why rotating the moves helps.
- Split by player (GroupKFold and GroupShuffleSplit), so testing is always on people the model has never seen. The notebook explains why a random split would leak information.
- Models: Categorical NB, Decision Tree, Perceptron, Logistic Regression and SVM. Baselines: random (33.3%) and always-rock (35.6%).
- Metrics: the same as Part 1, plus "accuracy right after a loss", expected to be about 53%.
- GridSearchCV with GroupKFold, cross-validation (mean ± std), and a learning curve over the number of training players. Keep "Run all" fast: tune the RBF SVM on a subsample or with a small grid (one RBF fit on 21K rows took about 30–40 s on a slow VM).
- **Personal learning:** an online per-player model, scored by window of rounds. Measured today: 46.1% over the first 50 rounds, 49.4% over rounds 50–150, 53.2% over rounds 150–300. Linear Regression (Lab 2) on accuracy against round number gives "the bot gets X points better per 100 rounds".
- Predict one new sample: "you just lost with rock against paper; what's your next move?"

Already measured on the brain data, with 5-fold GroupKFold on unseen players:

### Live game (Part 3)

**Screen** (my call): mockup B, "Face-off", from the brainstorm.
- Health bars, a ROUND banner, YOU (live camera) vs CHANAKYA (the bot).
- A result banner after each throw, a live win-rate line against the 33% luck line, and a dropdown for choosing the bot's brain.
- The match report reuses mockup C's table of every brain's accuracy.

**Round flow:**
1. The bot predicts the player's next move with the selected brain, using this player's history so far. It locks its counter-move before the countdown and shows it as a face-down card.
2. A spoken countdown, "Rock, paper, scissors, shoot!", using browser speech synthesis with on-screen captions.
3. At "shoot" the browser grabs one frame and sends it to Python:
   - OpenCV decodes the frame, MediaPipe finds the hand landmarks, and the Part 1 model classifies the gesture.
   - OpenCV then draws the hand skeleton on that frame and sends it back.
4. The reveal: both moves, the result, "I predicted ✊ ROCK (62%)" and a spoken taunt. The scoreboard and chart update, and the round is added to the history.

If no hand is found, it says "Show me your hand" and replays the round without counting it. Between rounds, a live label ("I see: ✌️") refreshes a few times a second; the builder sets the rate.

**Brains in the dropdown:** each Part 2 model, "Personal" (an online model that learns only from this player) and "Random". The default is the best Part 2 model, which the builder picks after measuring. Switching to Personal mid-demo is a planned moment.

**Match and report:**
- A match is 20 rounds (configurable).
- The match report shows the score and win rate against 33%.
- It shows the player's habits: repeat rate after a loss, tie and win; favourite move; which way they cycle.
- It replays the match through every brain to show which one read the player best.
- A "most unpredictable human today" leaderboard ranks the names typed in at the start of each match. Names live in session memory only.

**Mechanics:**
- An HTML/JS widget in a Colab output cell handles the camera (`getUserMedia` video), the canvas, the buttons and speech synthesis.
- It calls Python through `google.colab.kernel.invokeFunction`. All ML runs in Python.
- Frames are processed in memory and never saved, and the notebook says so.

**Accessibility:** every control works from the keyboard (Space starts a round), all speech has captions, and results are shown in text, never by colour alone.
